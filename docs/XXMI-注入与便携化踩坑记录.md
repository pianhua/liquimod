# XXMI 注入与便携化踩坑记录

## 目标

从 `v0.4.0` 重新对齐 LiquiMod 的 3DMigoto/XXMI 运行生态：

- 使用标准 XXMI/SRMI 核心布局；
- 让 `Mods` 只保存运行入口，真实 Mod 由 LiquiMod 仓库管理；
- 数据、日志、数据库和托管 3DMigoto 放在程序目录旁的便携数据根；
- 模组启动时直接走 XXMI 原生 Hook，不依赖 `3Dmigoto Loader.exe` 弹命令行。

## 关键踩坑与结论

### 1. 发行版主程序名称必须与 XXMI 配置一致

标准 `d3dx.ini` 的 loader 指向 `XXMI Launcher.exe`。如果实际发行文件仍叫旧的 `liquimod-app.exe`，或者配置中的 loader 名称不一致，Hook 链路会表现为游戏能启动但 3DMigoto 没有加载。

当前约定：

- 主程序：`XXMI Launcher.exe`；
- 运行目录：程序目录旁的 `3DMigoto`；
- XXMI 注入器：`Packages/XXMI/3dmloader.dll`；
- 运行目录中的 `Mods`：只放 LiquiMod 创建的 Junction/运行入口，不存放真实 Mod 内容。

### 2. StarRail.exe 的权限决定注入结果

本机实测中，普通权限启动 LiquiMod 时，XXMI Hook 返回早期/晚期错误码 `1`；使用发行版管理员清单后，注入成功，Mod 也能正常工作。

因此 Windows 发行版目前保留一次 UAC 提权：

- 发布版：`requireAdministrator`；
- 开发版：不强制提权，便于测试和前端开发；
- 注入验证：同时记录 `HookLibrary`、早期 `WaitForInjection`、窗口检测和晚期 `WaitForInjection`。

不要把“游戏进程已启动”当作“注入成功”。必须看到早期或晚期 Hook 校验成功。

### 3. 注入延迟应以官方 SRMI/XXMI 基线为准

`d3dx.ini` 的 `[System] dll_initialization_delay` 默认保持 `0`。随意增加延迟会改变初始化时序，可能造成“游戏能启动，但 Hook 或 Mod 不稳定”的假象。

### 4. 旧仓库清理必须幂等

迁移后旧路径可能已经不存在，也可能仍有用户备份。清理命令必须先校验路径，旧路径不存在时只清空旧路径元数据，不应把“找不到目录”当成删除失败。

### 5. 管理员窗口的拖放限制

当前发行版为了保证 StarRail.exe 注入而以管理员权限运行。Windows 会阻止普通权限的资源管理器把文件拖进高权限窗口；所以拖放事件可能完全不触发，日志中也不会出现 `install_mod` 或“已安装”记录。

这不是压缩包解析问题，也不是安装后端问题。当前可靠入口是主界面顶部的“导入”按钮，角色详情页还保留压缩包、文件夹导入和外部文件夹连接。

如果未来要恢复“资源管理器直接拖进管理员窗口”，需要把 UI 与注入权限拆成两个进程，并通过受控 IPC 让高权限进程只负责游戏启动/Hook；单纯在前端增加 HTML5 `drop` 事件不能绕过 Windows 完整性级别限制。

## 本次验证结果

- 用户实机确认：模组启动可以成功完成 XXMI 注入；
- 用户实机确认：Mod 在游戏中正常工作；
- 原生启动路径：不再依赖 `3Dmigoto Loader.exe` 命令行窗口；
- 安装后端：仍支持 `.zip`、`.7z`、`.rar` 与文件夹；
- 拖放失败时：使用顶部“导入”按钮继续完成安装，避免无提示卡死。

## 后续建议

1. 先保持当前管理员发行版作为稳定基线，不再同时修改注入权限和 Mod 部署逻辑。
2. 后续若要做真正的拖放恢复，单独建立“普通权限 UI + 管理员 Hook Helper”设计与测试，不要在当前工作版本上临时移除管理员清单。
3. Hash 冲突检测继续保持停用状态，避免把本次注入/安装收尾与冲突扫描混在一起。
